How To Use This Library

The map, the vocabulary and the working routine

00 Start Here Read this first

This library is the written memory of one vehicle and one expedition. It exists so that decisions already made do not have to be made again, and so that anything still unresolved is visible rather than remembered.

It is built from three layers. Almost every question about how to use it comes down to knowing which layer you are standing in.

Layer 1
Documents
What you read. Reference guides, country profiles, calculators, checklists, philosophy. All HTML, all offline, all printable. This is the library proper.
Layer 2
Registers
What tracks state. Plain text files that record what is still open, what each document is, and what the standing rules are. Not field reading — governance.
Layer 3
Data
The underlying record. Service ledger and audit working papers, both spreadsheets. Documents are derived from these, never the other way round.
The one rule that prevents most confusion Every fact has exactly one home. If a number appears in two places, one of them is a copy — and copies drift. When two documents disagree, do not average them. Find the owner. Section 08 gives the precedence order.

Where things live. Everything is on GitHub at github.com/Overlandslabs/Consumption and published to overlandslabs.github.io/Consumption. GitHub is the source of truth; anything on a laptop or phone is a copy that may be stale.

03 Finding Things Three routes in

There are three ways into the library and they answer different questions. Picking the right one is most of the skill.

I have a situationStart at the index

Open index.html. It is organised by what is happening to you, most urgent first: emergency and safety, then finding things, field tools, the vehicle, the expedition, countries, philosophy, governance. If something has gone wrong, the answer is near the top of the page.

I have a topicUse R30

The Cross-Reference Index (R30) is a searchable topic list across the whole library. It answers "which document covers tyre pressure / bilharzia / winching / carnets". It sits second on the index page for exactly this reason.

I have a wordSearch the page

Once inside a document, use the browser's own find function. Documents are single-page by design, so everything is on the page and searchable — nothing is hidden behind tabs or collapsed sections.

If you are alone and under pressure Go to the index and start at the top. The emergency section is deliberately first, and within it the order runs medical, vehicle dead, stuck, fire, security, wildlife, health — worst day first. You do not need to know any document numbers to use this library.

Printed copies. Every document prints properly. The critical few — the reference card and emergency procedures — are meant to be printed and laminated for the door pocket, because a flat phone is a foreseeable event.

04 The Registers What tracks state

Four governance files sit behind the library. They are plain text on GitHub rather than pages in the library, because they are working instruments rather than field reading.

Open Items RegisterThe one that matters most

The single authoritative list of everything unresolved. If something is not in here, it is not tracked, and a job that lives only in someone's memory or in a chat message does not exist.

Every entry follows one shape:

OI-n · Title · OWNER · GATE/DEADLINE · SOURCE · STATUS

Items are grouped into five categories:

CategoryWhat is in it
AOwner-gated actionsThings only Neil or Mary-Ann can do. Deadline-ordered. The real pre-departure workload.
BChartered workstreamsDocuments and systems still to be built.
CSmall fixes and defectsKnown faults awaiting repair.
DDecisions pendingWaiting on an owner ruling, not on work.
EStanding / recurringThings that never close — the monthly odometer reading, live working drafts.

Below the five categories sits the Controlled Duplication Register, and below that the closed log — every item ever closed, newest first, never deleted. The closed log is the reasoning archive: it records why something was decided, which is usually more valuable than the decision itself.

Checking open items quickly Open the register directly at
github.com/Overlandslabs/Consumption/blob/main/LC76_Open_Items_Register.txt
Then search the page for ▌A. through ▌E. to jump between categories, or for CLOSED LOG to find where the open items stop. Everything above the closed log is live.
A readable dashboard is planned Reading a hundred kilobytes of plain text to answer "what is still open" is the wrong instrument, and a proper filterable view is tracked as an open item in its own right. Until it exists, the method above is the fast route.
Controlled Duplication RegisterInside the OIR

A deliberately short list of facts that are allowed to appear in more than one document — emergency numbers, vehicle weights, licence dates, daily power draw. Each has one named owner and a mandatory list of everywhere it must be updated.

The rule: change the owner first, then sweep the whole propagation list in the same sitting. Never as a follow-up, never as a note for next time. This register exists because that discipline already failed once — a power figure drifted out of step with its own parts list in three separate documents and nobody noticed for weeks.

Project InstructionsThe standing rules

Vehicle specification, working conventions, design system, session protocol, and a narrative of recent sessions. Authoritative for doctrine. Older session narratives are archived into a separate history file so this one stays readable.

Library RegisterWhat exists

The definitive list of every document and its R-number. Check here before assuming a document exists or does not — the index page and any local copies can lag behind the repository.

Working papersAudit trail

A spreadsheet holding the technical-accuracy findings, the layout findings, the evidence sources behind them, and the programme tracker. This is the audit trail rather than a live task list.

05 The Loop How a change actually happens

Every change to this library runs the same seven steps. Knowing the shape makes it obvious where a piece of work has stalled.

1Finding. Something is wrong, missing or newly decided. It becomes an entry in the Open Items Register — immediately, in the sitting that found it.
2Ruling. If it needs a decision rather than work, it waits for an owner ruling. Decisions are recorded with their reasoning, so they are not re-argued later.
3Specification. For anything structural or spanning files, the full change is proposed and agreed before a single edit is made.
4Execution. Files are fetched pinned to an exact version, then edited surgically — never rebuilt from memory or from a local copy.
5Validation. Structural checks run before anything is delivered: tag balance, script syntax, unique anchors, and a sweep for stale text that must run wider than the change itself.
6Propagation. Everything that delegates to the changed fact is updated in the same sitting — the owner document first, then everything downstream.
7Registers and commit. The Open Items Register and Project Instructions are updated, dates bumped, and the whole set committed to GitHub together.
The failure mode this prevents A change that stops after step 4 leaves the library internally inconsistent and the registers claiming something untrue. A half-propagated change is worse than no change, because it looks finished.
06 Your Routine What to do and when
Every monthTen minutes
  • Read the odometer and log it — this drives service intervals across the whole library.
  • Glance at category A of the Open Items Register. Anything with a date approaching?
  • Glance at category D. Is anything waiting on a decision only you can make?
Before a tripPre-trip protocol
  • Work through the pre-trip preparation protocol and the departure checklist.
  • Print and laminate the reference card and emergency procedures for the door pocket.
  • Open the profile for every country on the route and check the data-freshness dates.
  • Confirm the phone has the library installed and working with the network switched off.
  • Check documents: licences, vehicle disc, insurance, and the owner's authority affidavit where a border is involved.
After a tripPost-trip review
  • Run the post-trip review protocol. This is the step that turns a trip into an improvement.
  • Record actual fuel, water and power consumption against what was planned.
  • Log anything that broke, anything missing from the kit, and anything carried and never used.
  • Open a new item for every finding. Close the ones the trip resolved.
  • Enter any service work in the service spreadsheet first, then refresh the derived documents.
If you do only one thing Log the odometer monthly and run the post-trip review. Those two habits keep the library honest; everything else can be caught up.
07 Working Sessions Owner-facing — skip if you are just reading

Changes to the library are made in working sessions with an AI assistant. One chat is one session. This section is how to run one.

Opening a sessionWhat to say

State the job and the file. The assistant fetches the live pinned version, proposes a change specification, and waits. Terse instructions are normal and expected — a single word is a valid approval once a specification is on the table.

You sayWhat happens
"Execute" / "Go"Autonomous execution within the agreed specification. Nothing outside it.
"Propose first"Full change map, no edits, until you rule.
"What's open?"A read of the register rather than a guess.
"Verify that"Check against the live file rather than against the narrative describing it.
What you should expect backQuality gates
  • A change specification before any structural or multi-file edit.
  • Governance files delivered complete, never as patches to hand-apply.
  • Validation results stated explicitly, not assumed.
  • Errors disclosed rather than quietly corrected.
  • A propagation list showing every file touched and why.
Two things to insist on Never accept an edit made against a local or remembered copy of a file — it must be fetched live and pinned. And never accept a number in a field document without a source; a plausible figure reads as authority, and an invented one in a safety document is the most dangerous thing that can be added to this library.

Big files. Anything very large gets its own session. Rebuilding a large document from fragments is how content is silently lost.

08 When Something's Wrong Precedence and reporting
Which source winsPrecedence order

When two sources disagree, this is the order. It settles almost every conflict without argument.

QuestionAuthority
Which version of a file is real?GitHub. Always. Any local copy, phone cache or attachment is a copy and may be stale.
Is this item open or closed?The Open Items Register. Not a narrative describing it.
What is the rule?Project Instructions. Nothing in the session history is a live rule.
Does this document exist?The Library Register. Not the index page.
What is this vehicle figure?The Facts file, or the owning document named in the Controlled Duplication Register.
How should a document look?Design Guidelines.
Reporting a faultWhat to capture

Anything counts — a wrong number, a broken link, a contradiction, a section that reads badly, a document that no longer matches reality. Note four things:

  • Which document, and roughly where in it.
  • What it says now.
  • What you think it should say, or simply why it looks wrong.
  • Whether it is dangerous. A wrong emergency number is a different class of fault from a typo.

That becomes an open item. It does not need to be diagnosed to be logged, and a suspicion is worth recording — several real defects in this library started as somebody saying that something looked odd.

Stale content on the phone If the phone shows an old version while the repository is current, that is the offline cache doing its job, not a lost edit. Close the app fully and reopen it with a signal. If a page is missing entirely in a fresh browser, that is a publishing problem rather than a caching one — two different faults with two different fixes.
Suspect the measuring instrument first When a check disagrees with a file, the check is wrong more often than the file. This has held true repeatedly. Confirm the fault exists before acting on it — a false finding costs more trust than the defect it claimed to catch.
