  overscroll-behavior-x:contain; -webkit-overflow-scrolling:touch;

  declarations. THE SCROLLBAR STAYS HIDDEN on desktop too (owner ruling,

  wraps is LATENT until someone adds a section — the Karoo file was fine

  footers, sticky nav always full browser width.

  anchors). Scroll offset must account for full sticky container height.
  IntersectionObserver for active-state highlighting.
- TOC INDEX CONTRACT (mandatory, adopted 22 Jul 2026 from OI-38;
  CORRECTED the same day after the first version of this rule caused three
  regressions). THE CONTRACT HAS THREE PARTS, NOT TWO: the sectionIds
  array, the TOC buttons, AND THE TOGGLE EXPRESSION that compares them.
  Read the toggle in the file before judging the pairing — do not assume it.
  Under toggle i===idx the array must mirror the TOC buttons exactly (same
  entries, same order, same length, including any alerts and changelog
  entries). Under toggle (i-1)===idx the array must be the TOC list MINUS
  its leading button, and an array that looks "short" is correct. Both
  conventions existed in this library and a rule written from one of them
  broke three files built on the other. STANDARDISED 22 Jul 2026: all ten
  profiles and the template now use i===idx with a 1:1 array, and any new
  profile inherits that from the template. If a future file is found on the
  offset convention, normalise it rather than adjusting the array. A mismatch does not throw; it silently highlights
  the wrong button, so it will never be caught by node --check or a depth
  walk. Two mirror-image failures were found in the profile family: an
  'alerts' id in the array with no button (003), and an "! Alerts" button
  absent from the array (006 and the TEMPLATE). ADD TO THE STANDARD
  VALIDATION SET: assert len(sectionIds) == len(tocLinks), assert every
  sectionIds entry resolves to a real element id, and verify the pairing in
  order. Whenever a section is added or removed, both lists change together.
  HOW TO EXTRACT THE TOC SIDE (learned the hard way, 22 Jul 2026 — two
  extractor versions gave false readings before the third was trusted):
  compare sectionIds against the getElementById TARGETS taken from every
  element carrying class="toc-link". Do NOT compare against button LABELS;
  do NOT assume the element is an <a>, because 009 Zimbabwe uses
  <span class="toc-link" onclick=...> and read as zero buttons; and do NOT
  anchor the pattern on attribute ORDER, because a class-first regex misses
  every file where class is the last attribute and will report most of the
  family as broken. The safe form is: find all tags matching
  <[a-zA-Z]+[^>]*class="toc-link"[^>]*>, then pull getElementById('X') from
  each tag. Both false readings were caught before being reported — working
  convention (d) doing exactly what it exists for.

- Ownership-first propagation (adopted 22 Jul 2026, from the content-audit
  seam pattern — the sharpest of the three structural findings). Before
  editing any topic, look it up in R30 and identify the OWNING document.
  Edit the owner FIRST, then every document that delegates to it, in the
  SAME session — never the reverse. R42-then-R10 is the failure mode that
  produced F38 (R42 corrected while R10 §3, which R42 delegates to, still
  carried superseded fire doctrine); R10-then-R42 would not have produced
  it. SESSION-CLOSE COMPLETENESS ASSERTION: for each topic touched, list
  the documents that delegate to it and assert each was visited, or
  explicitly deferred to a numbered open item — same control class as the
  COUNTIF baseline on the working papers. An R30 OWNER-flag column, which
  would convert this discipline from an act of vigilance into a lookup, is
  approved in principle and DEFERRED until after the Karoo loop.
- Report only what was actually executed (standing, 21 Jul 2026, ninth
  session). Claude states what it has ACTUALLY executed in the current
  session, verified against tool output, and never reports a session or step
  as complete from expectation (the ninth session opened with a prior turn
  wrongly asserting completed work that had not been done).
- Numeric traceability, self-audit, and verify-before-you-report (adopted
  22 Jul 2026 from the content-audit programme close). (a) Any specific
  numeric specification introduced into a library document must be
  traceable to Facts, the owning R-doc, or a manual — a plausible number
  reads as authority and is the most dangerous thing an assistant can add
  to a field reference (F65, a self-introduced defect). (b) A self-audit
  of prior-session Claude edits is a standing step in every audit session
  — it is the only control that caught F65. (c) A candidate finding is
  VERIFIED before it is written down; a false finding costs the owner's
  trust in the whole register (F74's dropped candidate). (d) Completeness
  checklists are written BEFORE the file is opened, never after.
- Experimental / pre-EX-9 route planning (adopted 13 Jul 2026): the expedition
  route is developed as an EXPERIMENTAL DRAFT that lives OUTSIDE the library
  until EX-9 ratifies it — kept in ordinary chats, NOT the project, so a fluid
  draft is never mistaken for committed fact. Source of truth = the working
  brief (LC76_Experimental_Route_OptionA_WORKING.docx / .md); the owner edits
  in place, and a "CHANGES THIS ROUND" list at the top of the doc is the
  reconciliation signal on re-upload (read it first, reconcile the body against
  it). The route MAP (…_MAP.html or the inline map tool) is a VIEW re-rendered
  from the brief on demand, NOT a persistent document — feedback goes to the
  brief, the map is redrawn (the inline map tool's "Day 1–6" labels are its
  fixed vocabulary; the HTML file says "Phase" and is the reference version).
  Iteration loop: edit brief in chat → when a version stabilises it becomes the
  EX-9 seasonal/route input → EX-9 ratifies → ONLY THEN propagate into the
  library (R38 §4, R39 §1, profile route framing). Nothing route-related commits
  to GitHub / the library pre-EX-9. These experimental artifacts are NOT library
  files, NOT precached, NEVER trigger a CACHE bump. Tracked as OI-26. Word docs
  are heavier to round-trip than markdown/txt — for fast iteration markdown or
  plain txt is the smoother medium; use Word only when the owner prefers the
  editing feel.
- Changelog discipline (owner ruling, 22 Jul 2026). (a) EVERY masthead
  "Last updated" bump carries a matching changelog entry — the masthead is
  the claim, the changelog is the evidence, and a claim without evidence is
  the defect class the content audit spent five sessions removing. This
  applies to silent fixes too: "TOC highlighting corrected, no content
  changed" is a valid entry. EXEMPTION, ADOPTED 29 JUL 2026 (owner ruling):

- Idempotence, not just anchors (standing, adopted 24 Jul 2026, from a live
  defect). `assert count == 1` proves the ANCHOR is unique; it proves
  nothing about whether the edit has already been applied. When a
  replacement CONTAINS its own anchor — the common case for "keep the old
  block and add a new one after it" — the guard passes on every re-run and
  silently duplicates the insertion. This happened on R32 on 24 Jul: a
  script re-run after two unrelated anchor failures applied the same block
  twice. Any script that might be re-run must ALSO assert that a
  distinctive string from the NEW content is ABSENT before writing, and a
  post-edit count of that string should be 1. Recovery is a SHA-pinned
  re-fetch and a single clean application.
- Encode before you truncate (standing, adopted 24 Jul 2026, from a live
  defect). Never write an edited file with open(path,'w') — that truncates
  the target the instant it is called, so any later failure (a bad encode, a
  lone surrogate in an emoji, an exception mid-write) destroys the file
  before a single validation gate has run. Encode the full string to bytes
  FIRST, confirm that succeeded, then write binary. The validation pipeline
  runs after the write and therefore cannot protect against this class at
  all; only the write pattern can. Recovery is a single SHA-pinned fetch,
  which is one more reason pinning is not optional.
