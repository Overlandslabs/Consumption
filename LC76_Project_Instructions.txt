TRUTH & PROPAGATION
- Ownership-first propagation (standing, adopted 22 Jul 2026). Before editing
  any topic, look it up in R30 and identify the OWNING document. Edit the owner
  FIRST, then every document that delegates to it, in the SAME session — never
  the reverse. SESSION-CLOSE COMPLETENESS ASSERTION: for each topic touched,
  list the documents that delegate to it and assert each was visited, or
  explicitly deferred to a numbered open item. An R30 OWNER-flag column, which
  would convert this discipline into a lookup, is approved in principle and
  DEFERRED until after the Karoo loop. Why: a delegate corrected while its
  owner still carries the superseded doctrine is how F38 happened.
- Report only what was actually executed (standing, 21 Jul 2026, ninth
  session). Claude states what it has ACTUALLY executed in the current
  session, verified against tool output, and never reports a session or step
  as complete from expectation (the ninth session opened with a prior turn
  wrongly asserting completed work that had not been done).
- Status-bearing content carries provenance (standing, adopted 29 Jul 2026,
  from OI-67). Any array, table or list in this library that asserts a live
  STATUS — outstanding actions, monitors, flags, "no record" claims — must carry
  a source field naming where each entry came from (manual, service history,
  owning R-doc, workshop advisory). COROLLARY FOR RECONCILIATION: a completeness
  gate must sweep for status-bearing content WHEREVER IT LIVES, not only in
  instruments that look like registers. Why: a list without provenance cannot
  be audited, therefore is not maintained, therefore drifts.
- Numeric traceability, self-audit, and verify-before-you-report (adopted
  22 Jul 2026 from the content-audit programme close). (a) Any specific
  numeric specification introduced into a library document must be
  traceable to Facts, the owning R-doc, or a manual — a plausible number
  reads as authority and is the most dangerous thing an assistant can add
  to a field reference (F65, a self-introduced defect). (b) A self-audit
  of prior-session Claude edits is a standing step in every audit session
  — it is the only control that caught F65. (c) A candidate finding is
  VERIFIED before it is written down; a false finding costs the owner's
  trust in the whole register (F74's dropped candidate). (d) Completeness
  checklists are written BEFORE the file is opened, never after. (e) Install
  facts are CONFIRMED AGAINST THE VEHICLE, never inferred from a
  manufacturer's typical layout (promoted 24 Sep 2026, PI restructure P2,
  from the fortieth/forty-first sessions — the MultiPlus switch order was
  inferred from the generic Victron layout and shipped wrong).
- Facts carry intervals; the gate flags overruns; overruns become tracked jobs
  (G2, standing, adopted 19 Sep 2026). A service-interval fact in LC76_Facts.txt
  carries an interval= field; lc76_fact_gate.py's OVERRUN tier flags any derived
  km-since that meets or exceeds its interval; every overrun is captured as an
  Advisories row (LC_Service_history_FINAL.xlsx) and, where a job is due, an OI.
  Maintenance monitoring is thereby an ENFORCED control, not a matter of vigilance.
- Release syncs facts, not conclusions (G3, standing, adopted 19 Sep 2026).
  lc76_fact_release.py updates fact VALUES only; it does NOT update the prose
  CONCLUSIONS drawn from them. A number crossing a threshold silently falsifies the
  sentence around it (in-interval becomes overdue). After ANY fact sweep,
  threshold-bearing conclusions MUST be reviewed; the OVERRUN gate names which facts
  crossed so the review is targeted. Case: the gearbox-oil "within interval" the
  odometer sync falsified, 18 Sep 2026.
- Sweep by corpus-wide enumeration against the master, never by value-hunting
  (G4, standing, adopted 19 Sep 2026). A fact is frozen on several stale bases
  across the corpus; searching for known stale VALUES misses copies on other bases
  (measured: a first R23 sweep was ~35% incomplete; the handover's file-list was
  ~half the real scope). THE CORPUS-WIDE GREP IS THE INVENTORY AND RUNS FIRST,
  before any tagging — a handed-down file list is not an inventory. Map every figure
  to its source EVENT; verify last-changed / work-done against the service ledger
  (master of work done), not a downstream doc; re-grep to zero at the end,
  documented exemptions excepted.
- Systemic verification, not human vigilance (G5, standing, adopted 19 Sep
  2026). Verification of maintenance status must be SYSTEMIC — a
  rejecter/gate — never dependent on a person noticing (extends "a schema is
  only real if something rejects violations"). Why: an odometer sweep surfaced
  three overdue drivetrain oils a stale document was calling "within
  interval", and the first sweep was itself incomplete.
- Content-currency is gated, not remembered (standing, adopted 22 Sep 2026).
  The fact gate catches NUMERIC drift and depth-walks catch STRUCTURE; NEITHER
  can see stale PROSE — a part swapped on the vehicle or a status that turned
  (planned->fitted). The rejecter for that class is lc76_currency_gate.py,
  driven by lc76_supersessions.txt: every real-world change that retires a term
  in the corpus is ONE old->new row in the log, and ADDING that row is what ARMS
  the gate — the list is DATA in the log, not code in a script. WORKFLOW: on any
  real-world entity/status change, add the supersession row FIRST, then fix the
  prose, then run the gate to zero fail-tier hits (warn-tier is surfaced for
  review — historical ledgers, comparison tables and correction notes are
  legitimate). It runs at session close beside the fact gate and is the
  enforcement arm of the Controlled Duplication Register for named-entity/status
  currency. HONEST LIMIT: it catches SUPERSESSIONS that go through the log, not
  brand-new fabrications; log-first is the discipline. Why: a gate the owner
  has to run in his own head is not a gate.
- Controlled Duplication Register (standing, adopted 23 Jul 2026). A short
  list, held in the Open Items Register, of facts permitted to exist in more
  than one document, each with ONE named OWNER and a mandatory PROPAGATION
  LIST. Any change to a registered fact triggers a sweep of that entire list in
  the SAME session — not a follow-up item — INCLUDING the derived values it
  drives. The rows (emergency numbers, SOS activation steps, GVM/kerb/payload,
  licence & disc dates, daily house load in Ah/day, electrical device names)
  and their propagation lists live in the OIR table, not here. ABSORBED BY THE
  FACT STORE (OI-107, 18 Sep 2026): each registered fact becomes a store entry
  cohort by cohort; a row is retired only once its fact lives in the store and
  its slots are tagged and gated. Why: it converts a latent seam into a lookup
  — two rows were added only after their facts had already drifted.
- Two-tier content placement — pattern vs incident (standing, 21 Jul 2026).
  Durable PATTERNS live in the topic reference doc; location-dated,
  perishable INCIDENTS live in the relevant country/terrain profile (the R35
  scam-pattern vs profile-incident split; mirrors R14/R40 strategy-vs-spanner
  and R14/TPMS strategy-vs-tool). Applies to any perishable, dated,
  place-specific observation.
- Section renumbering is decided by MEASUREMENT, never by rule (standing,
  24 Jul 2026). Before inserting a section into an established document, sweep
  the corpus for external §-references and anchor links into that document. Zero
  references → insert and renumber (the OI-36 profile case). References exist →
  append and point (the R35 §12 and R29 §13 cases). Both outcomes arose from the
  same test two days apart. Neither "always append" nor "always renumber" is a
  safe default; the sweep is cheap and settles it.

- Idempotence, not just anchors (standing, adopted 24 Jul 2026). `assert count
  == 1` proves the ANCHOR is unique; it proves nothing about whether the edit
  has already been applied. When a replacement CONTAINS its own anchor, the
  guard passes on every re-run and silently duplicates the insertion. Any
  script that might be re-run must ALSO assert that a distinctive string from
  the NEW content is ABSENT before writing, and a post-edit count of that
  string should be 1. Recovery is a SHA-pinned re-fetch and a single clean
  application.
- Encode before you truncate (standing, adopted 24 Jul 2026). Never write an
  edited file with open(path,'w') — that truncates the target the instant it is
  called, so any later failure (a bad encode, a lone surrogate in an emoji, an
  exception mid-write) destroys the file before a single validation gate has
  run. Encode the full string to bytes FIRST, confirm that succeeded, then write
  binary. Only the write pattern can protect against this class; recovery is a
  single SHA-pinned fetch, which is one more reason pinning is not optional.
- Archives are not reconstructed, and a redacted archive says so (standing).
  The Open Items Register and LC76_Session_History.txt are ARCHIVES. Their
  narrative is never altered, removed or rewritten after the fact — a
  correction is an ANNOTATION against the original sentence, not a replacement
  of it. (i) Withdrawing a VALUE is a different act from altering a RECORD, but
  an archive that has been redacted carries a DATED REDACTION NOTICE naming the
  class of data withdrawn, stating that no narrative was altered, and noting
  that prior commits still hold the originals. (ii) A missing session is
  recorded as a LABELLED, DATED GAP and sessions are NEVER RENUMBERED to close
  it — renumbering would silently re-point every existing cross-reference. Why:
  a reconstructed record reads as contemporaneous when it is not (the F65 class
  applied to governance).
